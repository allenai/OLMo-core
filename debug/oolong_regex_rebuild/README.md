# oolong `--item-regex` rebuild — investigation, verdict, and validated recipe

**Date:** 2026-08-12. Read-only against the pre-migration repo; nothing committed, nothing pushed.

**Verdict, in one line: the CTC-suite `oolong_train` shard really is defective, but it does NOT
need rebuilding — a clean, `query-position after` oolong training shard already exists as part of
the 5-task suite (`xlong5_qafter`, built 2026-08-11). Reuse that. The new
`ctc-data build` → `convert_to_shards.py` path was validated end-to-end at pilot scale and is also
clean, but running it at full scale would produce a *narrower, differently-split* dataset than the
known-good one.**

---

## 1. The defect is real, and it is confined to the CTC-suite shard

Independently re-measured this session (not taken on trust from the earlier record), reading each
shard's raw `token_ids_part_000000.npy` node-locally and decoding with the Qwen3.5-4B tokenizer.
Two signatures, both from `scan_oolong_shard.py` in this directory:

* **inter-chunk FREE tokens** — any token between `<|box_end|>` and the next `<|box_start|>` that
  isn't an example boundary. It bridges two chunks the mask is supposed to isolate.
* **chunks vs ITEM lines** — oolong is line-based, so exactly the `Date: … || User: … || Instance: …`
  lines should be wrapped. Chunks in excess of item lines are preamble lines wrongly wrapped.

| shard | built | examples (part 0) | chunks/ex | FREE gaps/ex | chunks − item_lines | verdict |
|---|---|---|---|---|---|---|
| `/data/prasann/ctc_suite/shards/oolong_train` (cubbins, mooney) | **2026-07-19** | 2540 | 347.6 | **5.000** | **+5, +5, +5** | **LEAK** |
| `/data/prasann/xlong5_qafter/shards_chunked/oolong_train` (horton) | 2026-08-11 | 15037 | 113.7 | 0.000 | 0, 0, 0 | CLEAN |
| pilot rebuild via `ctc-data` + `convert_to_shards.py` (this session) | 2026-08-12 | 500 | 119.1 | 0.000 | 0, 0, 0 | CLEAN |

The bad shard's first chunk decodes to the **instruction line** —
`"Read the data below and answer the question. Compute the exact answer by analyzing every item; …"` —
which should be FREE prefix, not a chunk. The clean shards' first chunk is a real `Date: …` item.
Exactly 5 extra chunks and exactly 5 FREE gaps per example, in every example: the `'||'` signature
(instruction / question / header / repeated-question lines wrapped, with the blank lines between
them left FREE).

**`metadata.json` could not settle this on its own.** The pre-migration converter never recorded
`item_regex`, so the 2026-07-19 shard's metadata looks identical to a good one. The evidence had to
come from the token stream. (The ported `convert_to_shards.py` fixes this: its `metadata.json` now
records both `item_regex` and `query_position` — see `pilot_metadata.json` here.)

## 2. The guard in the new repo

`src/scripts/ctc/convert_to_shards.py::check_item_regex` (called only for `--chunk-by line`) rejects
**any regex that matches the empty string**, which is the general form of the defect rather than a
blacklist of `'||'`. Verified live — passing `--item-regex '||'` exits before tokenizing with:

```
--item-regex '||' matches the EMPTY STRING, so it matches every line: the instruction/question/
header lines would each be wrapped as their own chunk and the blank lines between them would stay
FREE, bridging chunks and mismatching the eval layout. Did you mean '\|\|' (escaped) rather than '||'?
```

The same check exists eval-side in `ctc/src/ctc/eval/prefill.py:105`, and `ctc.tasks.oolong.spec`
pins `extra={"chunk_by": "line", "item_regex": r"\|\|"}`, so train and eval segmentation agree by
construction.

## 3. Why NOT to rebuild: the 5-task suite already ships the good shard

`/data/prasann/xlong5_qafter/shards_chunked/oolong_train` (horton; also on weka/S3 as
`prasanns/xlong5_2k256k_qwen35_qafter/`) was built 2026-08-11 by
`debug/xlong5_qafter/tokenize_all.sbatch` in the pre-migration repo:

```
--emit dense --task oolong --chunk-by line --cot-mode none --query-position after
--marker-set qwen3_5 --tokenizer /data/prasann/hf_models/Qwen3.5-4B-Base
--seq-len 250000 --shard-tokens 100000000        # NO --item-regex (default r"\|\|")
```

19 972 instances / 348 M tokens, `query_position: after` recorded in its metadata, 0 leaks measured
above. Its source pools are `xlong5/pools/oolong`, generated by
`src/corpus_reasoning/data/generate_oolong_ladder_data.py` over 7 length bands 2 048 → 254 280.

It is also the audited in-domain partner of the v2 oolong eval (all 10 source sub-datasets on both
sides, matching `task_group`/`answer_type` mixes, item density 0.0187 train vs 0.0206 eval).

## 4. Divergences: old 5-task build vs new `ctc-data build --task oolong`

The new generator is a faithful port of the task logic — same 9 exactly-recomputable variants, same
`MIN_ITEMS=4`, same `QUESTION_RESERVE=220`, same greedy token-budget draw, same tie-retry — but the
*ladder* and the *pool split* differ, and both differences matter:

| axis | 5-task `xlong5_qafter` (known good) | new `ctc-data build --task oolong` |
|---|---|---|
| length ladder | 7 bands, `T ~ U[LO_b, HI_b]`, contiguous **2 048 → 254 280**; counts 6000/5000/4000/2700/1400/600/300 | 5 rungs {2k,4k,8k,16k,32k}, 4000 each; `T ~ U[300, rung]` — **caps at 32 768** and skews short inside every rung |
| instance-length cap | `--seq-len 250000` (max instance 249 226) | pilot max 33 699 |
| pool `max_context` | `--pool-max-ctx 262144` | default `131072` (overridable: `-C max_context=262144`) |
| item-count tokenizer | Qwen3.5-4B-Base | default `Qwen/Qwen3-0.6B` (overridable: `-C tokenizer=…`) |
| train/eval item split | **none at generation.** Overlap handled post hoc by `decontaminate_oolong_train.py`, and the shipped `qafter` build deliberately used the **un**-decontaminated pool | `OolongPool.for_split("train")` holds out 10 % of items per sub-dataset **by construction**, so a new build draws from a different item substrate than the v2 eval was built from |
| source sub-datasets | all 10 | all 10 — verified identical: agnews, app_reviews, formality, imdb, metaphors, multinli, negation, spam, trec_coarse, yahoo |
| queries per context | 1 | 1 |
| converter flags | identical (see §3) | identical, plus the `item_regex` guard and `item_regex`/`query_position` in metadata |

So a full `ctc-data` rebuild would be **clean but not equivalent**: shorter maximum context, a
short-skewed length distribution, and a different item substrate that breaks the audited
train/eval pairing. That is a worse trade than reusing a shard that is already correct.

## 5. What was actually run

All on `cubbins` (has the 12 GB `oolongbench/oolong-synth` arrow cache at
`/data/prasann/hf_cache`, `/data/prasann/hf_models/Qwen3.5-4B-Base`, the conda env, and internet)
and `horton`, node-local, via `srun`. Nothing on NFS, nothing on Beaker.

```bash
# pilot generation (72 s incl. 90 s-cold pool load; 500 examples -> 10.7 MB train.jsonl)
export HF_HOME=/data/prasann/hf HF_DATASETS_CACHE=/data/prasann/hf_cache
export PYTHONPATH=<newrepo>/ctc/src
python -m ctc.data.cli build --task oolong --split train --train 500 \
    --out /data/prasann/oolong_rebuild_pilot

# pilot conversion (37.7 s, 16 procs, 3.38 M tokens -> ~90 k tok/s)
python <newrepo>/src/scripts/ctc/convert_to_shards.py \
    --task oolong --emit dense --chunk-by line --cot-mode none \
    --marker-set qwen3_5 --tokenizer /data/prasann/hf_models/Qwen3.5-4B-Base \
    --query-position after --seq-len 40960 --shard-tokens 50000000 --num-proc 16 \
    --input-jsonl /data/prasann/oolong_rebuild_pilot/oolong/train.jsonl \
    --out-dir /data/prasann/oolong_rebuild_pilot/shards_train
```

Artifacts: `/data/prasann/oolong_rebuild_pilot` on cubbins (12 MB total). Its `metadata.json` and
`ctc_format_fingerprint.json` are copied here as `pilot_metadata.json` /
`pilot_format_fingerprint.json`. The pilot is **validation of the path, not a deliverable dataset**
— do not train on it.

`scan_oolong_shard.py` reproduces every row of the §1 table:

```bash
python scan_oolong_shard.py --shard <shard_dir> --parts 1 \
    --tokenizer /data/prasann/hf_models/Qwen3.5-4B-Base --decode-examples 3
```

## 6. If a full `ctc-data` oolong build is ever wanted anyway

Measured, not guessed: pool load ~90 s cold / ~50 s warm, generation ~15 s per 500 examples,
conversion ~90 k tok/s per 16 procs. A 20 000-example build is ≈ 135 M tokens ⇒ **~10 min generate
+ ~25 min convert at 16 procs (~13 min at 32)**, so ~25–40 min wall on one cubbins node.

```bash
srun -p jsteinhardt -w cubbins --qos=preemptive_high -c 32 --mem=200G -t 02:00:00 bash -lc '
  export HF_HOME=/data/prasann/hf HF_DATASETS_CACHE=/data/prasann/hf_cache
  export TOKENIZERS_PARALLELISM=false PYTHONUNBUFFERED=1
  REPO=<newrepo>; export PYTHONPATH=$REPO/ctc/src
  PY=/data/prasann/conda/envs/corpus-reasoning-olmo/bin/python
  OUT=/data/prasann/oolong_ctc_v3
  $PY -m ctc.data.cli build --task oolong --split train --train 20000 \
      -C max_context=262144 -C tokenizer=/data/prasann/hf_models/Qwen3.5-4B-Base --out $OUT
  $PY $REPO/src/scripts/ctc/convert_to_shards.py \
      --task oolong --emit dense --chunk-by line --cot-mode none \
      --marker-set qwen3_5 --tokenizer /data/prasann/hf_models/Qwen3.5-4B-Base \
      --query-position after --seq-len 250000 --shard-tokens 100000000 --num-proc 32 \
      --input-jsonl $OUT/oolong/train.jsonl --out-dir $OUT/shards_chunked/oolong_train'
```

Note `--split train` alone leaves `eval_examples` empty, so `build_train`'s gold-fingerprint guard
cannot fire; the item-level `for_split` hold-out is the only separation in that mode. Build
`--split both` if you want the guard as well — but then the eval half is a *new* eval set, not the
v2 one, and the comparability argument in §3 is gone.

## 7. Recommendation

1. **Do not use** `/data/prasann/ctc_suite/shards/oolong_train` (2026-07-19) for anything, and treat
   every oolong number measured on it as measured on defective data — it needs a retrain, not a
   re-eval.
2. **Use** `xlong5_qafter/shards_chunked/oolong_train` (or `shards_full/` for the no-marker arm) as
   the CTC oolong training data. It is clean, `query-position after`, covers 2k–250k, and is
   in-domain with the v2 eval.
3. Keep the `check_item_regex` guard and the new `item_regex`/`query_position` metadata fields —
   together they make this defect both unrepeatable and, for the first time, detectable from a
   shard's own metadata.
